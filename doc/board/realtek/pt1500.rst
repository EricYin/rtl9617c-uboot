PT1500
======

The PT1500-H10 is a Youhua home gateway, sold as China Telecom firmware
PT1500R_V6.05.1001. U-Boot is the BL33 stage of the platform firmware and
provides the boot path plus the browser based recovery environment.

Hardware
--------

* Realtek RTL9617C, chip id 0x6706, revision 66, 64-bit ARM, 512 MiB DRAM
* Winbond W25N02KV, 256 MiB SPI NAND (block 128 KiB, page 2048 + 128 OOB,
  single-bit IO)
* Four GE ports, each on its own RTL8211 PHY at MDIO address 1 to 4
* Port 4 runs HSGMII to an RTL8367SB switch; U-Boot does not bring it up, and
  the recovery service never needs it
* Cortina UART0, 115200 8n1, 125 MHz input clock
* Reset key on bank 4 bit 8 (global GPIO 136), active low
* Status lamps LED_EPHY0..3 on bank 3, bits 6, 7, 1 and 4, active high

The GPIO controller has five banks of 32 pins; pin numbers in the device tree
here are global, so 136 is bit 8 of bank 4.

Building
--------

.. code-block:: bash

   export CROSS_COMPILE=aarch64-linux-gnu-
   make pt1500_defconfig
   make

This produces ``u-boot.bin`` (``u-boot-nodtb.bin`` with the device tree
appended) and ``u-boot.dtb``. As on the other boards, U-Boot is only the BL33
payload: the images have to be wrapped into the platform FIP together with BL2
and BL31 by the platform flashing tooling.

Storage layout
--------------

The physical partitioning is the platform one; see :doc:`partitions`. This
product's UBI volume table is:

===== ================== =========== ==============================
Id    Volume             Size        Contents
===== ================== =========== ==============================
0     ubi_Config         7.0 MiB     factory, calibration, ITMS identity
1     ubi_DTB0           380 KiB     slot A device tree
2     ubi_k0             6.0 MiB     slot A kernel (FIT)
3     ubi_r0             30.0 MiB    slot A rootfs (SquashFS)
4     ubi_DTB1           380 KiB     slot B device tree
5     ubi_k1             6.0 MiB     slot B kernel (FIT)
6     ubi_r1             30.0 MiB    slot B rootfs
7     ubi_framework1     16.1 MiB    framework SquashFS
8     ubi_framework2     16.1 MiB    framework SquashFS
9     ubi_otherConfig    17.1 MiB    other configuration
10    ubi_apps           97.0 MiB    application stack
11    ubi_BakConfig      3.0 MiB     backup configuration
===== ================== =========== ==============================

Volumes 0, 9 and 11 hold device identity and configuration and are never
removed by a rebuild.

Environment
-----------

``board/realtek/<board>/<board>.env`` holds only what is specific to the
hardware: the recovery network defaults and the load address. The boot policy -
``bootcmd``, the boot menu entries, the kernel command line - is set by
``rtk_board_env_init()`` in code, identically on every board, so an erased or
unreadable environment cannot change how the board boots.

The environment is stored once, at 0x200000, without a redundant copy.

Boot flow
---------

``bootcmd`` is ``bootmenu 3`` on every board, with the same two entries:

* ``Start OpenWrt`` runs ``rtk_boot``: attach UBI, read ``ubi_k<slot>`` for the
  slot named by the ``slot`` variable (default 0), set ``bootargs`` from the
  layout and boot the FIT configuration the board descriptor names for this
  unit's variant.
* ``Web recovery`` runs ``rtk_recovery``.

Holding the reset key at power on starts the recovery instead, and a key pressed
after power-on is still caught just before ``bootcmd`` runs.

Recovery
--------

.. note::

   The image ships LZMA-compressed inside a self-decompressing BL33 stub
   (``loader/``, built by ``./build-bl33.sh``): that is what makes this
   ~70 KiB service fit the BL33 slot the stock firmware leaves (see
   :doc:`boot-chain`). The service is enabled in the shipping configuration.

The recovery environment is the HTTP service (``CONFIG_CMD_HTTPD``): a single
page on 192.168.0.1 with a built-in DHCP server, supporting RAM uploads and
downloads, command execution, whole-flash restore, kernel and boot-area
installation, boot of an uploaded FIT and reset.

Writes are range, alignment and bad-block checked before any erase, and the
details live in ``board/realtek/common/``; the board only says which pins are
the lamps and which volume names the product uses.

There is no longer an install job for the vendor's own upgrade archive: the
service writes a kernel FIT into the slot volume and leaves the rest of the
flash to the storage endpoints, which is all the layout needs.

Source layout
-------------

The board is one of three layers; see :doc:`porting` for the split. Everything
this port adds lives in:

* ``arch/arm/dts/rtl9617c-pt1500.dts`` - board nodes: reset key, flash
  partitions, recovery layout
* ``board/realtek/pt1500/board.c`` - DRAM banks and init; nothing else
* ``board/realtek/pt1500/desc.c`` - lamps, key and FIT configuration
* ``board/realtek/pt1500/layout.c`` - volume table and kernel command line
* ``board/realtek/pt1500/pt1500.env`` - default environment
* ``configs/pt1500_defconfig``, ``include/configs/pt1500.h``

Everything else is shared: ``arch/arm/mach-taurus/``, ``drivers/`` and
``board/realtek/common/``.
